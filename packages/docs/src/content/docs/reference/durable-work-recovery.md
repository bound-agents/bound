---
title: Durable work recovery
description: Inspect local durable work and redrive dead letters with the workspool sandbox command.
---

Use `workspool` in an agent sandbox to inspect a host's local durable-work spool and redrive dead letters after you have identified a recoverable failure. The command operates only on the current host; durable work is not synchronized between hosts.

## Command reference

List dead-lettered work and pending or processing work older than one hour:

```text
workspool list
```

Set the stale threshold in milliseconds when investigating a crash or stalled consumer:

```text
workspool list --stale-ms 300000
```

Each result includes the row ID, kind, age, idempotency key, claim state, attempt count, last error, and a bounded payload preview. `list` surfaces dead-lettered rows, stale `pending`/`processing` rows older than the threshold, and `transferring` rows that have been transferring longer than the stale threshold — a wedged spool transfer whose acknowledgement never returned. `list` never changes a row.

Redrive one dead letter by ID:

```text
workspool redrive --id ROW_ID
```

Redrive every dead letter of one registered kind:

```text
workspool redrive --kind client_tool --all-dead-lettered
```

A redrive returns the row to `pending` and clears its claim generation. A **dead letter** keeps its attempt count and resets its expiry from the registered kind TTL; a redrive does not directly invoke a handler, the normal consumer claims the row, and rows without a registered kind are rejected because their expiry cannot be determined. A **stale `transferring`** row (a wedged spool transfer) is reclaimed the same way but **charges one attempt** and **respects the attempt cap** — a row already at the cap is dead-lettered (transfer-retry exhausted) rather than re-pended, so a row the receiver keeps failing to acknowledge marches toward its dead-letter cap instead of looping; no registered-kind gate applies because the row already carries the RPC TTL its producer set. Once `pending`, the sender's spool push and the next drain re-send it to the target.

Purge local residue that will never drive to completion, without dropping to `sqlite`:

```text
workspool purge --kind client_tool --dead-lettered
workspool purge --all-unclaimed --older-than 3600000
workspool purge --all-unclaimed --force
```

`purge` physically deletes rows — correct because `durable_work` is local-only and never synced, so there is no tombstone contract to honor. It reaches rows of **any** target: the whole table is host-local (the `local` sentinel only distinguishes in-process dispatch wakeups from peer-transfer rows, it does not mark "rows in this table"), so peer-targeted dead letters — `result`, `inference`, `platform_request`, `cancel`, `client_tool` — are cleared too, which is the backlog this command exists for. Two selectors, both narrowable with `--kind`: `--dead-lettered` removes terminally-classified dead letters (`--older-than` filters them by age; no floor, they are already failed and kept only for inspection/redrive), and `--all-unclaimed` removes `pending` rows (and dead letters) that no consumer holds. `--all-unclaimed` **never touches `processing`, `transferring`, or `consumed` rows** — a `processing`/`transferring` row is actively owned and deleting it would race a live consumer or a recoverable transfer, and a `consumed` row is an idempotency fence the periodic prune retires on its own schedule. The one-hour pending floor is a **hard gate** without `--force`: `--older-than` can only make the window narrower (older rows only), never reach younger than the floor, so a legitimately slow-to-drain wakeup is never destroyed as if it were residue. `--force` lets `--older-than` apply as given (`--all-unclaimed --older-than 0 --force` deletes every unclaimed row regardless of age). **A pending peer-targeted row is the durable spool-transfer queue, not residue.** The MSI outage of 2026-08-31 proved these rows can stay `pending` and healthy for days across a peer outage and still deliver the moment the peer reconnects — deleting them as stale wakeups would destroy undelivered work. So `--all-unclaimed` **excludes peer-targeted pending rows entirely without `--force`**: only `local`-targeted pending rows (dispatch wakeups) are eligible under the plain selector, subject to the same one-hour floor. `--force` widens eligibility to peer-targeted pending rows too, still respecting `--older-than` as given — an operator reaching for `--all-unclaimed --force` against an old peer backlog is making the deliberate judgment that the transfer queue is genuinely dead, not merely slow. Peer-targeted **dead letters** carry no such protection: they are terminal, so `--dead-lettered` and `--all-unclaimed` both clear them regardless of target and without `--force`. `purge` reports the deleted count per invocation. Reach for it when `list` shows accumulated dead letters or orphaned pending rows the automatic sweeps do not reclaim; the periodic prune deletes dead letters only after their seven-day retention deadline, and it never age-purges pending work at all — that judgment is yours.

## Operations runbook

Redrive dead letters after a transient outage has ended and you have checked the row's error and payload preview. Inspect stale pending or processing rows after a crash; restart recovery or the owning consumer may resolve them without a redrive.

Do not redrive a row when its payload describes an action that is no longer safe, when the error indicates invalid input or a permanent authorization failure, or before the failed dependency has recovered.

A `not found or already consumed` result is a safe no-op. Consumption retires the row, and a redrive does not recreate it. The durable `(kind, idempotency_key)` fence also prevents duplicate receipt during normal delivery and transfer.

When a passive intake binding has been removed, its durable intake rows become dead letters instead of being discarded. They remain visible to `workspool` and can be redriven after the binding is restored.

Rows targeted `local` (dispatch wakeups) are consumed in-process by the owning host and are never spool-transferred to a peer. Startup recovery resets any `local`-targeted row found in `transferring` back to `pending` — that state is unreachable through the spool protocol, so such a row is a stranded wakeup, and the reset logs one `[recovery]` warning with the row count. Peer-targeted `transferring` rows are deliberately left untouched at boot; the sender resumes them with its retained token on reconnect.

A peer-targeted row can still wedge at `transferring` while the process keeps running: the `SPOOL_TRANSFER` shipped but no `SPOOL_TRANSFER_ACK` returned, and the reconnect drain only re-sends on a fresh connection, so a persistently-connected sender whose ack was dropped has no automatic retry. Three recovery legs close this, all driven by the sync transport's periodic sweep (every 30 seconds, and again whenever a peer (re)connects). The **terminal-expiry** leg runs first and unconditionally: any non-dead-lettered row past its `expires_at` — `transferring`, `pending`, or `processing` — is dead-lettered into a seven-day, redrivable dead letter, so a short-TTL row that expires before it is ever transfer-stale still surfaces in `workspool list` instead of sitting invisibly wedged. The **transfer-reclaim** leg then returns a `transferring` row whose transfer has been outstanding past the 30-second transfer window — measured from `claimed_at`, not the work's own TTL, and only while the row is still live (`expires_at` in the future) — to `pending`, charging one attempt, then re-drives every live peer, so the stall clears within a sweep interval without a reconnect. A row at the shared attempt cap dead-letters instead of requeueing. The two legs never race over one row: a terminally-expired row belongs to expiry alone, a still-live one to transfer-reclaim. Stale `processing` rows are never *reclaimed* automatically — the owning consumer may still be executing, and reclaiming the row would run the work twice; boot recovery covers dead consumers, and a genuinely wedged processing row is an investigate-first decision followed by `workspool redrive --id` (an expired processing row is still dead-lettered by the terminal leg, since its consumer deadline has passed). The third leg is **flip-only-when-sendable**: a row flips `pending → transferring` only for a send that reaches the socket. When the channel is live but backpressured and the frame is refused, the begun-but-unsent generation is rolled back to `pending` under its token (no attempt charged — nothing crossed the wire), so it is never left transferring with no in-flight frame; the next drain or write-push retries. The refusal itself must be able to clear on its own: a spoke's send channel latches `pressured` when its socket buffer crosses the backpressure limit, and — unlike the server, which resets on the WebSocket `drain` event — the client has no drain event, so the latch is advisory. Every send re-polls the live buffer and clears the latch once it has drained below the limit, and the receive-side liveness timer proactively clears a stale latch and re-drives the spool toward the hub, so a single backpressure blip can no longer refuse every transfer until the next reconnect. A subtler failure needs a different tool, because the client `send()` carries no per-frame delivery signal. A spoke's socket can read `OPEN` per `readyState` yet be dead over TCP for up to the receive-side liveness window (300 seconds) before the idle watchdog forces a reconnect, and on such a socket Bun's client `send()` neither throws nor flushes — the frame is queued into the socket buffer and never leaves. That queueing is **not** a per-frame failure signal: a healthy socket over a slow WAN, or one buffering under TLS, also queues a frame transiently and still delivers it, so `send()` reports success on any queued-but-not-thrown write and the flip-only-when-sendable rollback fires only on the pre-existing refusal conditions (socket not `OPEN`, latch engaged, or `send()` threw). Treating a single-send buffer delta as a refusal would instead livelock the spool — every briefly-queued transfer would roll its row back to `pending` and invalidate its generation token, so no row would ever hold a `transferring` token long enough for its ack to retire it. The dead socket is caught out-of-band by **buffer-stall persistence**: a dedicated detector runs on its own 30-second cadence — aligned with the transfer sweep, deliberately faster than the 60-second receive-liveness cadence — and force-closes a socket whose buffer stays non-zero and non-decreasing across two consecutive checks while nothing is backpressured, a parked-but-not-flushing dead socket. The 30-second detector cadence bounds the phantom-success window: two consecutive stuck-buffer checks (~60 seconds) force-close and reconnect deliberately faster than the 120-second receive-liveness fallback, without waiting out the full liveness window and without raising the attempt cap. It does NOT provably beat the transfer sweep's attempt cap. The detector and the sweep run on independent timers with independent phases, so an unlucky alignment can still charge a parked row to the cap and dead-letter it inside the detection window — worst case, a row already near the cap when the socket silently dies. That residue is recovered automatically by a fourth leg, **reconnect auto-redrive**: when a peer reconnects, before the drain re-sends anything, every dead letter this exact failure mode produced — `last_error` of `transfer retries exhausted (no SPOOL_TRANSFER_ACK)`, targeted at the reconnected peer, dead-lettered within the last 15 minutes — is returned to `pending` with its attempt count reset to zero (the prior attempts measured a channel now known to have been dead, not the work), so the fresh live channel re-drives it in the same pass. This auto-redrive is itself budgeted: a per-row `reclassify_count` (persistent, capped at three) is charged once per reconnect that reclassifies the row, so a row that keeps dead-lettering is auto-redriven at most three times before it stays dead-lettered for operator `workspool redrive` — the reset attempt count can no longer terminate it and the sliding recent-window fence never would, so this budget is its terminal deadline. The window and the transfer-exhaustion `last_error` fence this to rows that failed on the just-proven-dead channel recently enough that no operator has triaged them; dead letters from terminal expiry, consumer failures, or older transfer exhaustion are real and left untouched. When a dead letter falls outside that narrow set — anything the auto-redrive does not reclaim — `workspool redrive --id ROW_ID` remains the manual recovery path. When you need to act before the sweep, `workspool list` shows wedged transferring rows by `claimed_at` age and `workspool redrive --id ROW_ID` reclaims one immediately, charging an attempt and observing the same cap. On the receive side, the receiver classifies each entry's insert by fault. A single **validation-failing** entry (a malformed identity field, or a payload that decoded to non-JSON on the wire) is skipped and warned per entry, never poisoning the batch or the connection: the good siblings insert and ack, the malformed entry is not acked (leaving the sender's normal retry-to-cap and transfer-exhaustion dead-lettering to give it the correct disposition), and that validation failure never reaches the connection-closing dispatch catch. A genuine **local storage failure** on insert — disk full, corruption, schema drift, a closed database, a constraint breach — is a different class entirely: it is not swallowed, it escapes the handler to the ws-server dispatch catch that closes the connection with 1011 by design, because a host whose own store is broken should sever the link rather than warn once per entry per retry while the sender keeps re-sending forever.

A durable request or response row's terminal TTL (`expires_at`) is never shorter than its kind's registry-declared TTL. RPC request kinds declare the RPC-class window (300 seconds), but a caller passes its own request timeout — a platform or client-tool request can carry a timeout of only a few seconds. A terminal TTL shorter than the 30-second transfer window would be self-defeating: the row would expire before it could ever be transfer-reclaimed, so the producer clamps `expires_at` up to at least the registry TTL. The clamp is a floor, not a ceiling — a caller that wants a longer live window keeps it — and a kind with no declared TTL (dispatch wakeups, task firings) keeps the caller's value verbatim.

## Roll back new dispatch enqueues

Set `BOUND_DURABLE_DISPATCH=0` (or `false`) before starting Bound to route new dispatch wakeups back to the legacy `dispatch_queue` during a recovery rollback. Durable rows already written remain readable and are drained first; do not delete them to make the rollback take effect. Remove the variable or set any other value to return new enqueues to durable work.

Bound always writes relay and intake work to `durable_work`. A non-advertising peer hop is a typed routing error, not a fallback. Self-targeted work uses the local target and never transfers to a peer.

### Startup refusal on populated legacy relay tables

A host reaching a release-N+1 binary with a legacy `relay_outbox` or `relay_inbox` table that still holds rows completes one of three paths at boot, decided per table by classifying each row rather than counting them all. The gate is boot-safety-conservative: it drops a row only when that row is **provably** safe, and treats everything else as **live** so no ambiguous row is silently discarded. Two provably-safe buckets: a **consumed** row is already delivered/processed (`delivered`/`processed` equals `1`, the marker release-N code wrote — not merely non-zero, so a hand-migrated `''` or `'garbage'` in that column on a non-STRICT table is *not* mistaken for consumed), and an **expired** row is undelivered/unprocessed (`= 0`) but carries an `expires_at` that is a well-formed ISO 8601 timestamp — a full year-through-seconds shape that SQLite's own `datetime()` parser accepts as a real instant — whose **parsed instant** is at or before now. The comparison normalizes both sides through `datetime()` (`datetime(expires_at) <= datetime(now)`) rather than sorting the raw strings: a timestamp carrying a non-UTC offset like `2026-09-03T20:00:00-05:00` names an instant five hours later than its wall-clock fields read, so a raw-string compare against a `Z`-suffixed now would misjudge it and could drop live work — the normalized-instant compare classifies it by the moment it actually denotes, not by lexical order. A date-shaped prefix like `2026-01-01Tgarbage`, an out-of-range `2026-99-99T00:00:00`, or a `0000-00-00T00:00:00` is **not** proof of expiry: the shape check plus the `datetime()` parse reject all three, so they stay live. An expired row's requester timed out its await long ago, and the TTL is the delivery contract. **Live is the arithmetic remainder** (`live = total - consumed - expired`), so it captures not only genuinely undelivered-and-unexpired work but also any row the safe buckets cannot claim: a NULL or malformed `expires_at`, a NULL / non-`1` `delivered`/`processed`, anything of indeterminate state. That remainder guarantees the three buckets always sum to the row total, and it means a row is refused unless it is provably dead. The classifier and the operator's inspection query are built from one shared set of SQL predicates, so the advertised query returns **exactly** the rows the classifier counted live — never a subset that omits the indeterminate ones.

- **No table present** — clean boot. This is the healthy N→N+1 path after the release-N drain-and-drop gate dropped the tables.
- **Table present, no live rows** (empty, or holding only expired/consumed residue) — Bound logs one structured warning naming the per-table breakdown (e.g. `dropping legacy relay_outbox: 8 rows, all expired/delivered residue (8 expired, 0 delivered); no live work — safe to drop.`), drops the table, and boots. Dead residue never bricks the boot.
- **Table present with one or more live rows** — Bound refuses to start. The error names the live/expired/consumed breakdown per table and includes the exact inspection SQL to list the live rows. That SQL is the complement of the two safe buckets (`NOT provably-consumed AND NOT provably-expired`), built from the same predicate fragments the classifier used, so running it returns precisely the live rows the message counted — including any with a NULL or malformed `expires_at` or a NULL `delivered`/`processed` that a naive `WHERE delivered = 0 AND expires_at > now` would have hidden.

The refusal does **not** assume the host "skipped" release N. "Tables empty after drain" can fail to hold even on a host that ran release N for days: rows addressed to a peer that went offline or was never upgraded can never deliver, so the 4E drain gate never releases. Because those rows carry short TTLs, they are usually expired junk by boot time — which is exactly why the classification path drops them cleanly instead of refusing. A live-row refusal means genuinely undelivered, unexpired work is still queued, and rolling back to release N does not converge on its own if the target peer stays offline. The message gives two remedies:

1. **Roll back to the release-N binary** (the first version shipping legacy-relay drain-and-drop, `hasDroppedLegacyRelayTables` / commit `5aaecbd3`) — but only if the target peer(s) can come back online to drain the live rows. If they stay offline, release N cannot drain them either.
2. **Manually export/delete the live rows** if they are addressed to a permanently-gone peer (they can never deliver), then restart the release-N+1 binary, which will then find no live rows and drop the empty table cleanly.
Set `BOUND_TASK_FIRE_MODE` before startup to control how the scheduler fires due scheduled tasks. Three states: `durable` (the default) is the end-state execution path — the rendezvous winner enqueues a `task_fire` durable_work row instead of performing the in-process phase-1 claim, and the same-tick consumer lane claims that row and bridges the legacy `pending → claimed` CAS into task execution, so the synced `tasks` row lifecycle is unchanged and a firing runs exactly once; `compare` is a rollback posture that runs the legacy in-process phase-1 claim-and-run path unchanged and, in addition, records comparison telemetry (a `task_fire_comparison` log line plus the `bound.scheduler.task_fire.comparison` counter) for the would-be durable enqueue decision without writing any durable row; `legacy` is the other rollback posture — the in-process phase-1 claim-and-run path alone, byte-identical to pre-consolidation behavior, with no telemetry. Any unset or unrecognized value is treated as `durable`. In `durable` mode a firing not claimed before its TTL (5 minutes) dead-letters into workspool-redrivable state, the intended failure surface for a wedged scheduler; a firing whose binding re-armed before it was claimed no-op-consumes at claim time against the live row, so re-arms produce fresh firings and superseded instants retire cleanly.
