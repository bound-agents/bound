# Common Gotchas

Accumulated the hard way — check here before writing a bug report. [CONTRIBUTING.md](../CONTRIBUTING.md#common-gotchas) carries the one-line index; this file carries the full writeup for each.

### AI SDK inputTokens is the summed total, not non-cached input

Across both Bedrock and Anthropic providers, the AI SDK's `usage.inputTokens` aggregates `noCache + cacheRead + cacheWrite` into a single number. The non-cached portion (what AWS bills at the full input rate, matching CloudWatch's `InputTokenCount`) lives on `usage.inputTokenDetails.noCacheTokens`. `extractUsage` in `packages/llm/src/ai-sdk-bridge.ts` reads from `inputTokenDetails.noCacheTokens` first and falls back to `inputTokens` only when details are absent. This means `StreamChunk.done.usage.input_tokens` (and downstream `turns.tokens_in`) is non-cached only — the three fields `tokens_in`, `tokens_cache_read`, `tokens_cache_write` are independent, NOT components of the same total; the full wire prompt size is the sum of all three. The agent-loop's inflation EMA at `applyActualUsageToContextDebug` deliberately sums all three back into `actualTotalTokens` because cache reads + writes occupy wire bytes (they're discounted in pricing, not absent from the prompt). Pre-fix (commit `ae09084b`), `calculateTurnCost` double-charged the cached portion at the full input rate; real AWS cost was ~50% of what `turns.cost_usd` recorded for cache-heavy turns. Verified live via 7-day CloudWatch reconciliation: DB-derived `noCache = tokens_in_pre_fix - cache_read - cache_write` matched `InputTokenCount` within 0.4% on opus. Historical `turns.cost_usd` rows are not backfilled — they're recorded with the old semantic and self-correct as new turns land.

### global.fetch pollution in tests

Tests that mock `global.fetch` (e.g., Ollama driver tests) MUST save and restore it in `afterAll`, or sync integration tests start failing with mysterious network errors.

### TUI frame-capture tests and ambient stdout state

`packages/less` tests render Ink components through `ink-testing-library` and assert on the plain-text frame from `lastFrame()`. Two ambient `process.stdout` signals can corrupt those frames depending only on *how the suite was launched* — a piped run (CI, an editor task) renders clean, while a real terminal (an interactive `git commit` driving the pre-commit hook) does not, which reads as a "flake" that won't reproduce in isolation. (1) **Color level**: chalk derives its level from `process.stdout.isTTY` when `FORCE_COLOR` is unset, so the inverse-video cursor cell and colored tool prefixes leak SGR codes into the frame and break `toBe` / `toContain`. `scripts/test-preload.ts` pins `FORCE_COLOR=0` for the whole run to make this deterministic; don't rely on a test's own `isTTY` state for color. (2) **TTY-gated control writes**: a component that emits terminal control sequences (e.g. mouse-tracking enable) must gate on the TTY-ness of the stream it *writes to* — Ink's injected `useStdout()` stream — not the global `process.stdout`. Gating on `process.stdout.isTTY` while writing to the injected capture stream leaks the control bytes into `lastFrame()` whenever the ambient stdout is a TTY. See `useScrollableMessages.ts` and its regression test.

### SQLite datetime vs ISO 8601

Never compare `datetime('now', '-Nh hours')` (which returns `2026-03-28 22:23:33`, space-separated) against JS `toISOString()` timestamps (`2026-03-28T22:23:33.091Z`, `T`-separated). ASCII `T` > ASCII space, so all ISO dates appear "newer". Always compute cutoffs in JS: `new Date(Date.now() - N * 3600_000).toISOString()` and pass as a parameter.

### Zod v4 z.record needs two arguments

`z.record` requires two arguments — `z.record(keySchema, valueSchema)`. Single-arg calls don't type-check.

### Typecheck is per-package

There is no composite mode at the root, so `bun check -b` from the root fails with TS6306 ("must have setting composite"). Run `bun check --no-script -p packages/<name>` for one package, or `bun run typecheck` for all of them — `scripts/typecheck-all.ts` runs each package's `typecheck` script in turn and reports every failing package. Pass `--no-script` whenever you invoke `bun check` directly: the root `package.json` has a `check` script (the full pre-commit gate), and without the flag `bun check` runs that script instead of the type checker.

### bun test cli prints init stdout

`bun test packages/cli` prints init-test stdout — use the exit code to check success, not `grep`.

### Mixed positional and flag arg parsing

`packages/sandbox/src/commands.ts` still hand-parses argv for MCP bridge commands, the only commands still dispatched through the bash sandbox. It assigns bare tokens to the next unfilled positional in declaration order, treats a `--flag` followed by another `--flag` (or by nothing) as boolean `"true"`, and accumulates repeated flags only when the command opts in. A flag value that begins with `--` therefore gets read as a second flag. Native agent tools take structured JSON parameters and avoid this class of bug.

The Stricli migration (`2cbf3082`) does not cover this parser. It replaced argv scanning in `bound`, `boundctl`, and `boundless`, where flags may now follow positionals and unknown flags exit 1.

### loopContextStorage scope (AsyncLocalStorage)

`loopContextStorage` is exported from `@bound/sandbox`. Commands running inside the agent loop see `threadId` / `taskId` in context automatically. Commands invoked outside (e.g., boundctl) don't.

### bound CLI config and data dirs

The bound CLI config dir defaults to `./config` (relative to cwd) and data to `./data`. Use `--config-dir` / `--data-dir` to override, or run from the directory where your config lives.

### Stale binaries

`just install` (build + atomic swap into `~/.local/bin/`) is the install step — see the `install` recipe in the repo's `justfile` for why it's not a plain `cp dist/bound* ~/.local/bin/` (macOS 26+ AMFI SIGKILL race on stale cached pages at the same inode). Running a stale compiled binary in one shell while iterating on source in another has burned us repeatedly. Check `bound --version` if behavior doesn't match source.

### Universal 256 KiB tool-result cap

Every tool result, regardless of `kind`, is bounded by `capToolResultContent` (from `@bound/shared/strings.ts`, `MAX_TOOL_RESULT_BYTES = 256 * 1024`) at two boundaries — the agent-loop dispatch return (covers platform/sandbox/builtin and the legacy fallback) and `handleToolResult` in `packages/web/src/server/websocket.ts` (covers WS-deferred client tools from boundless / external `BoundClient` consumers). Truncation is middle-cut with the marker `[truncated N bytes from middle; tool result exceeded 262144-byte cap — re-run with a narrower scope or pipe through head/grep]`; the marker's byte width is subtracted from the half-budgets so the function is idempotent and the output is guaranteed ≤ cap. If a tool result looks like it's missing a chunk, grep for the marker — that's the cap firing, not a bug. Per-tool caps still run first; this is a backstop, not the primary ceiling.

### Oversized bash output offloads to a file

Offload fires at `50KB`, before the 256 KiB cap. Both bash surfaces offload to a file when the assembled result exceeds `TOOL_RESULT_OFFLOAD_THRESHOLD` (`@bound/shared/src/offload.ts`, `50_000` chars), rather than middle-cutting it. The full output is written to disk and the in-context result is replaced with a short pointer (`buildOffloadMessage`, shared) telling the agent where to `cat`/`grep` it — so nothing is lost, it just leaves the context window. The destination is the only surface-specific bit: the sandbox/agent path writes to a VFS path (`/home/user/.tool-results/<toolCallId>.txt`, `offloadToolResultPath` in `packages/agent/src/tool-result-offload.ts`, applied in the agent-loop dispatch offload loop), and `boundless_bash` writes to a real local temp file (`os.tmpdir()/bound-tool-results/<uuid>.txt`, `offloadIfOversized` in `packages/less/src/tools/bash.ts`). Threshold and pointer-message format live in `@bound/shared` so the two surfaces cannot drift. If `boundless_bash` can't write the file, it falls back to inline output and the universal 256 KiB `capToolResultContent` backstop still applies. Historically (`cfe8aa22` … `3b088b77`) both surfaces middle-cut each stream at ~50KB via `truncateStreamOutput`; that fought the agent-loop offload loop (the cut shaved bytes below the offload threshold before offload saw them) and was reverted in favor of offload-on-both-surfaces. If bash output is missing and you see a `[Tool result offloaded: …]` pointer, that's this — read the named file.

### query accepts PRAGMAs

The agent `query` tool allows `SELECT` plus a small read-only PRAGMA allowlist (`table_info`, `index_list`, `foreign_key_list`, `integrity_check`, etc.; see `SAFE_PRAGMA_ALLOWLIST` in `packages/agent/src/tools/query.ts`). The `PRAGMA x = y` assignment form is rejected regardless of name. Anything else (INSERT/UPDATE/DELETE/ATTACH/unknown PRAGMA) errors out. `LIMIT 1000` is still auto-appended to SELECTs but skipped for PRAGMAs.

### Thread interface tag

POST `/api/threads` accepts an optional body `{ interface?: string }` (default `"web"`, regex `/^[a-z0-9-]+$/i`, ≤32 chars; 400 otherwise). The value lives in `threads.interface` and flows into the agent's volatile context as a platform tag. `isUserFacingInterface()` in `@bound/shared` (`packages/shared/src/interface-tags.ts`) is the single gate for "should the agent see `platform: <name>`?" — currently allows everything except `scheduler` and `webhook` (the canonical exclusion list lives in the same module as `NON_USER_FACING_INTERFACES`, also used by the `POST /api/threads` color cycle to skip system-driven threads when picking the next palette color). Adding a new user-facing surface usually needs no code change beyond setting the tag on thread creation; adding a new system-driven surface means extending the filter. `BoundClient.createThread(options?: { interface?: string })` is the client-side counterpart — `boundless` sets `interface: "boundless"`.

### Cross-provider tool_use portability (id and name)

`tool_use.id` and `tool_use.name` values persist in the `messages` table and survive provider switches. Anthropic enforces `^[a-zA-Z0-9_-]+$` on `tool_use.id` and rejects the entire request when a historical id contains anything else; Bedrock Converse caps both `toolUseId` and `toolUse.name` at 64 chars and validates them against `[a-zA-Z0-9_.:-]+` and `[a-zA-Z0-9_-]{1,64}` respectively. Two pathologies have been observed in production:
   1. **Charset (Kimi/Moonshot fallback ids)**: the OpenAI-compatible path, where the AI SDK synthesizes ids from `function.name + index` when the upstream emits no explicit id, routinely produces ids of the shape `functions.<name>:<index>` containing `.` and `:`. When such a thread later routes to opus or Bedrock-Anthropic, the API returns `messages.N.content.M.tool_use.id: String should match pattern '^[a-zA-Z0-9_-]+$'` and the turn fails.
   2. **Length+charset (Kimi/Moonshot template-token leakage, thread `81bd5e8d` 2026-05-21)**: the same path occasionally streams Moonshot's own `<|tool_call_argument_begin|>` template token mid-stream as plain text, and the AI SDK collapses the entire template fragment into the synthesized `tool_use.id` and `tool_use.name`. Persisted ContentBlocks end up with 200+ char id and name fields containing `<`, `|`, `>`, `{`, `}`, `"`, spaces, etc. The next turn fails with 6 simultaneous Bedrock validation errors (`Member must have length less than or equal to 64`, `Member must satisfy regular expression pattern: …`) on both the `toolUse` and the matching `toolResult`. The thread cannot self-recover and the task cannot be restarted without losing state.

**Fix:** universal sanitization in two layers, both deterministic and idempotent.
  - **Streaming boundary** (`mapChunks` in `packages/llm/src/ai-sdk-bridge.ts`): `tool-input-start` / `-delta` / `-end` events run their `id` and `name` through `sanitizeToolUseId` and `sanitizeToolName` (the latter from `stream-utils.ts`) before yielding the corresponding `tool_use_start` / `_args` / `_end` `StreamChunk`s. Fresh tool calls therefore land in the DB already wire-legal. A `logger.warn` fires only when length truncation occurs (`sanitized.length < input.length`); charset-only diffs are expected steady state for AI SDK fallback ids and would spam logs. Both `BedrockDriver` and `OpenAICompatibleDriver` pass `providerName` into `MapChunksOptions` so the warn log identifies which provider is leaking.
  - **Read boundary** (`toModelMessages` in the same file): same sanitization is re-applied at all four sites — assistant `tool_call`-role tool_use parts, inline assistant content tool_use parts, `tool_result.tool_use_id`, and the `toolNameById` index keys + values. Idempotent on freshly-sanitized data, but **the recovery mechanism for already-poisoned historical rows**: a thread that pre-dates this fix self-heals on the next assembly without manual DB surgery or task recreation. The original DB content is preserved for auditability — only the wire projection is rewritten.

`sanitizeToolUseId` (`[a-zA-Z0-9_-]{1,64}`, exported alongside `MAX_TOOL_USE_ID_LENGTH`) and `sanitizeToolName` (`[a-zA-Z0-9_-]{1,64}` with `unknown` empty fallback) both target the strict subset across every supported provider's accepted charset and length cap, so universal sanitization is lossless on the wire and avoids per-provider branching. When adding a new id-bearing or name-bearing field at the bridge boundary, route it through these helpers too.

### OpenAI Responses reserves tool names (`tool_search`, `shell`, …)

The OpenAI Responses API reserves a set of tool names for its provider-defined server tools, and `@ai-sdk/openai`'s Responses input converter (`convert-to-openai-responses-input.ts`) special-cases an assistant tool-call part **by name** when the resolved name is one of them: `tool_search`, `shell`, `local_shell`, `apply_patch`, `computer`. `tool_search` is the dangerous one — the converter emits a provider-defined `tool_search_call` input item for it **unconditionally** (the others gate on a matching `has*Tool` flag that is only set when the corresponding provider-defined tool is registered). A Bound client tool whose name collides is then serialized as a `tool_search_call`, while its plain-text result still flows through the generic branch as a `function_call_output`. The output's `call_id` has no preceding `function_call` (only a `tool_search_call`, which pairs with `tool_search_output`), so the Responses `input` union rejects the whole request at the wire with `Invalid 'input': value did not match any expected variant` (HTTP 400, after the SDK's local `validatePrompt` passes). Live incident: gpt-5.6-sol, 2026-10-10, a 108-message all-text transcript carrying historical `tool_use` blocks named `tool_search` — three orphaned outputs, no media involved.

**Fix:** the OpenAI Responses path uses a dedicated `OPENAI_RESPONSES_ENVELOPE` (not the shared `PERMISSIVE_ENVELOPE`) that carries `reservedToolNames: OPENAI_RESPONSES_RESERVED_TOOL_NAMES`. `sanitizeToolNameForEnvelope` suffixes any colliding name with `RESERVED_TOOL_NAME_SUFFIX` (`_fn`) after the charset/length transform, deterministically, so the escape lands identically at every site the name appears (assistant `tool_use`, the `toolNameById` index that resolves `tool_result` names, and the live toolset via `toToolSet`). The `/chat/completions` paths (openai-compatible, opencode-go) keep `PERMISSIVE_ENVELOPE` with no `reservedToolNames` — those endpoints have no reserved server-tool names, so escaping there would be gratuitously lossy. When adding a provider whose wire converter special-cases tool names, give it an envelope with the matching `reservedToolNames` set rather than renaming globally.

### thinking-signature portability

`thinking` ContentBlocks persist in the `messages` table and replay on later turns the same way `tool_use` ids do. Bedrock-Anthropic and Anthropic-direct reject any `thinking`/`reasoning` block on the wire that lacks its cryptographic `signature` with `messages.N.content.M.thinking.signature: Field required` (Bedrock `ValidationException`, 400, not retryable) — the whole turn fails, and there is no signature to synthesize after the fact. A persisted thinking block can lack a signature two ways:
   1. **Same-provider signature loss** — a turn that streamed reasoning text but never captured the signature event. This is the observed 2026-06-06 incident: a fresh thread targeting opus (`global.anthropic.claude-opus-4-8`) from the start, where exactly ONE assistant turn (of 679 on that host, 14,085 cluster-wide) persisted a thinking block with no signature, immediately before the failing replay. A singleton, not a systematic capture or relay bug — the root cause of the loss on that one turn is unconfirmed (the block's thinking text ended mid-sentence and a text block resumed mid-sentence, consistent with an interrupted/interleaved reasoning capture, but unproven).
   2. **Cross-provider replay** — a thinking block produced by a non-Anthropic model (local, OpenAI-compatible, non-Anthropic Bedrock), legal with no signature for the model that made it, that later routes to an Anthropic target.

  The fix covers both, since the illegal wire state is identical regardless of origin.

  **Fix (read boundary, `buildReasoningPart` in `packages/llm/src/ai-sdk-bridge.ts`):** when the target requires a signature (`reasoningProviderOptions` is `"bedrock"` or `"anthropic"`) and the block has neither a `signature` nor a Bedrock-replayable `redacted_data`, the reasoning part is dropped — both `toModelMessages` call sites (assistant `tool_call`-role parts and inline assistant content parts) skip the `null` return. Dropping is the only legal move and is safe: an assistant `tool_call` turn carrying no reasoning block is accepted by Bedrock-Anthropic even when a `tool_result` immediately follows it — verified against production, where 34,847 opus `tool_call` turns with no thinking block at all have replayed without error. The inline text / tool_use in the same assistant message is unaffected, so the turn keeps its substance and loses only the unreplayable reasoning trace. Like the `tool_use` sanitization, this is the **recovery mechanism for already-poisoned historical rows** — any thread holding a signature-less thinking block (whether from cross-provider replay or a one-off same-provider capture loss) self-heals on the next assembly against a strict provider without DB surgery. A Bedrock redacted-reasoning block (`redacted_data`, no signature) IS legally replayable via `providerOptions.bedrock.redactedData` and survives; non-signature targets (`reasoningProviderOptions: null` / unset) never demand a signature, so signature-less blocks replay as bare reasoning text there.

### boundless_bash runs inside a filesystem sandbox by default

Shell commands launched through boundless's `bash` tool use seatbelt on macOS, bubblewrap on Linux, and Bound's native one-shot AppContainer lowbox on Windows. The whole filesystem stays readable while writes are confined to the working directory, temporary directories, and configured extras. Windows never selects mxc BaseContainer or IsolationSession. If lowbox setup fails — including when host policy blocks unprivileged `CreateAppContainerProfile` — `onUnavailable: "error"` refuses the command with an actionable message; `"passthrough"` is the only fallback and emits a `ran UNSANDBOXED` warning.

Three consequences bite during development. (1) A host whose backend cannot start fails closed by default. Set `"sandbox": { "onUnavailable": "passthrough" }` only to opt into unsandboxed execution, or `"sandbox": false` to disable confinement. (2) Tests that write outside cwd or `$TMPDIR` fail with `EPERM` when run through boundless even if they pass in a plain terminal; use `os.tmpdir()` instead of hardcoded paths. (3) `.git/config` and `.git/hooks` remain read-only even though the rest of the working tree is writable. On Windows the lowbox helper enforces this with scoped DACLs, including nested existing hook paths, while preserving ordinary writes to `.git/index`, refs, logs, and objects. The Windows CI oracle also proves allowed-root writes, sibling/traversal/junction denial, descendant-tree cancellation, and watcher-owned profile/ACL/journal cleanup. Configure the policy in `~/.bound/less/config.json`.

### Sandboxed commands can kill their own processes but cannot list them

Under mxc 1.1.0 the generated seatbelt profile allows signals between processes in the same sandbox (`(allow signal (target same-sandbox))`), so `kill $!`, `timeout`, `killall`, and Bun's `child.kill()` work against the command's own descendants, and `MxcProcess.kill()` reaps the whole descendant tree in one call. A backgrounded `sleep` grandchild, and one that traps SIGTERM, both die with the root. Measured through `boundless_bash` on macOS: `sleep 12 & kill $!` exits 0, `timeout 2 sleep 8` returns 124 after 2 s, and a `nohup sleep 300 &` left behind by one tool call is gone before the next call starts.

The remaining caveat is discovery, not signalling. The profile denies process-table access: `ps` fails with `Operation not permitted`, and `pgrep`/`pkill` fail with `Cannot get process list` (exit 3). Inside the sandbox, target a process by a pid you already hold (`$!`, `child.pid`, a pidfile) or by name with `killall`; don't build a teardown on `pgrep`/`pkill` or a `ps` scan, which silently finds nothing. Under mxc 0.7.0 the profile allowed `(target self)` only, so `timeout -k 15 120 bun test ...` exited on schedule while its child kept running; on 2026-11-19 several orphaned `bun test` processes, about 7 GB each, froze the host (#277).

The client-side reaper stays as a belt-and-suspenders fallback and for the UNSANDBOXED bash path, which runs a plain `Bun.spawn` with no mxc containment and still needs host-side tree reaping. `SandboxSpawnResult.kill` on the sandboxed path (`packages/less/src/tools/sandbox.ts`) calls the host-side tree reaper (`packages/less/src/tools/process-tree.ts`) first, then `MxcProcess.kill()`; on the unsandboxed path (`spawnUnsandboxed` in `bash.ts`) only the tree reaper applies. The reaper reads the host process table, signals every descendant's process group and pid, and remembers groups so a later SIGKILL still reaches survivors reparented to init. Regression test: `packages/less/src/__tests__/process-tree.test.ts`; its live cases skip inside a sandbox and run in CI.

Bun 1.4.5's `bun --no-orphans` (valid on `bun`, `bun run`, and `bun test`) partially closes this from the other side: a `--no-orphans` process exits when its own parent dies and SIGKILLs every descendant on the way out — the SIGKILL overrides a child's SIGHUP/SIGTERM ignore handler. Measured inside this sandbox: a `bun --no-orphans victim.ts` spawned by a short-lived intermediate parent died the instant that parent exited, while the same victim without the flag kept running until the tool call itself ended. This is exactly the orphan case — a pre-commit test run whose launcher is killed or exits no longer survives. The pre-commit gate (`.githooks/pre-commit` → `bun --no-orphans run scripts/test-affected.ts`), the two `bun --no-orphans test` spawns inside `scripts/test-affected.ts`, and the root `package.json` `test` script carry the flag. It does not remove the need for the client-side reaper: a process whose parent is itself orphaned, or killed with SIGKILL (no chance to propagate), still needs `SandboxSpawnResult.kill`. CI is unchanged — its runners already reap their own process trees.

### An mxc 1.1.0 sandbox cannot start inside another seatbelt sandbox

mxc 1.1.0 runs the sandbox in-process: `run()`/`spawn()` load `libmxc_ffi.dylib`/`.so` via koffi and call `sandbox_init(3)` inside the boundless client process itself (0.7.0 instead shelled out to a separate `mxc-exec-mac` executor). A process already under a seatbelt profile cannot apply a second one — `sandbox_init` fails with `Operation not permitted` — so a boundless whose own shell is sandboxed cannot spawn an mxc sandbox for its tools. This is why the per-thread `/sandbox off` override exists: when you are working on the sandbox itself (or anything that must run an inner mxc sandbox), `/sandbox off` drops the thread's commands out of the outer confinement so the inner `sandbox_init` can succeed. The symptom of forgetting is `checkSandboxAvailable()` reporting unsupported with an `Operation not permitted` / `sandbox_init` reason, and every sandboxed spawn failing before it runs. Linux bubblewrap has the analogous nesting constraint (unprivileged user-namespace nesting), so the same `/sandbox off` escape applies there.

mxc 1.1.0 needs two Bun-specific workarounds, both covered by `packages/less/src/__tests__/sandbox.test.ts` and `dist/mxc-sandbox-probe`. First, `spawn()` wraps the child's stdout/stderr pipe descriptors in `net.Socket({ fd })`, which never emits data under Bun, and `fs.createReadStream` fails on them with `EAGAIN` because they are non-blocking. `patches/@microsoft%2Fmxc-sdk@1.1.0.patch` reads them with `Bun.file(fd).stream()` instead and closes the fd when the stream closes. Second, writes to `/dev/null` fail on both backends, which breaks every `>/dev/null` redirect and `git status`, for different reasons. 1.1.0's seatbelt profile denies them, so `writableDevices()` in `sandbox-policy.ts` grants `/dev/null`, `/dev/zero` and `/dev/fd` on macOS. Under bubblewrap, a readonly grant on `/` becomes a bind mount inside a user namespace, where the kernel forces `nodev`, and it lays a copy of the host `/dev` over the private one bwrap builds; `readableRoots()` therefore grants every top-level directory except `/dev`, `/proc` and `/sys` on Linux. Both failures left exit codes at 0, so a sandboxed command looked successful with empty output.

Hostname lookups are a third 1.1.0 regression on macOS. `getaddrinfo(3)` goes through mDNSResponder over Mach IPC, and 1.1.0's seatbelt profile blocks `com.apple.dnssd.service`, so `ssh`, `git push`, `curl` and `bun install` all failed with resolution errors even with the network open, while `nslookup` (which sends its own UDP queries) and connections by IP still worked. With the network open, `sandbox-policy.ts` grants the resolver Mach services (`DNS_MACH_LOOKUPS`) and lists the `/private/var/run/mDNSResponder` socket in `readwritePaths` (`dnsSocketPaths`), since mxc's profile only grants `network-outbound` to a Unix socket path through that list.

In a compiled binary on Linux, 1.1.0's `getPlatformSupport()` cannot run its `bwrap --version` probe: it `import()`s `dist/bwrap-probe-worker.js` from the SDK package on disk inside an eval'd worker and re-spawns `process.execPath` with two more package scripts, none of which exist under `bun build --compile`. Bubblewrap then reports unavailable ("Cannot find module '/dist/bwrap-probe-worker.js'"). `scripts/mxc-bwrap-probe-plugin.ts` patches the SDK's default runner at compile time to call `globalThis.__boundBwrapVersionRunner`, which `packages/less/src/tools/bwrap-version.ts` sets to a bounded `spawnSync("bwrap", ["--version"])`. The SDK's version parsing and minimum-version gate still run on its output. The build fails loudly if the patch anchor disappears from a future SDK.

### Mantle GPT-5.x automatic prompt cache is exact-match, not prefix

Mantle's automatic prompt cache does not do longest-prefix matching. Verified live against `bedrock-mantle.us-east-2` (2026-07-04) by replaying **exact captured request bodies** with raw SigV4: an identical body resent back-to-back reports ~100% `cached_tokens` (44,613/44,644), so the cache and the usage-reporting chain both work — but a **prefix-extension** request sharing 99.3% of the prior prompt (which is what every agent-loop inference is: same prefix, appended tool results) reports `cached_tokens: 0` even back-to-back on the same connection. The lookup behaves as if keyed on the full prompt rather than longest-prefix — almost certainly a serving-layer bug or regression, not intended semantics: OpenAI-operated endpoints do longest-prefix matching, the endpoint accepts `prompt_cache_retention: "24h"` as if prefix caching were supported, and Codex session records show ~88% cache-read rates against an earlier mantle us-west-2 deployment (since removed), proving the stack prefix-cached before. Corroborating details: identity resends hit only within a seconds-scale window (connection affinity; ≥15–20s idle → miss), `prompt_cache_key` does not influence routing, responses carry no affinity cookie/header, and the Codex CLI pointed at the same endpoint measures the same ~0% on its own multi-turn sessions. Consequences: (1) on gpt-5.4/5.5 — which only have the automatic cache — no request-shape change fixes it: `prompt_cache_retention: "24h"`, `store: false`, and the reporting path are already correct (see the `buildMantleOpenAIOptions` docstring in `packages/llm/src/drivers/bedrock-mantle.ts`), so treat those models as uncacheable at conversation depth when picking models for long sessions; the Anthropic/Converse legs cache normally. (2) The GPT-5.6 family additionally accepts up to four explicit `prompt_cache_breakpoint` markers per request (`{ mode: "explicit" }`, serialized by `@ai-sdk/openai`'s chat and Responses converters from `providerOptions.openai.promptCacheBreakpoint`), which key the cache at the marked boundaries instead of the full prompt — sidestepping the exact-match lookup entirely. The mantle driver sends them on 5.6 models (`supportsPromptCacheBreakpoints()` in `packages/llm/src/drivers/bedrock-mantle.ts`): a system-anchor breakpoint on the instructions message plus the bridge's position-aware attacher (`attachOpenAIPromptCacheBreakpoint` in `packages/llm/src/bridge/messages.ts`), which places each `{role:"cache"}` marker at the nearest wire-expressible slot (system message-level, user part-level, tool-output item-level; assistant items have no slot — the marker walks back), capped at `MAX_OPENAI_MESSAGE_BREAKPOINTS = 3` message-level markers so the system anchor always fits within the four. (3) The earlier finding that replayed `reasoning_encrypted_content` is nonce-varying is real but moot until the endpoint's prefix matching is fixed. Because the exact-match behavior is a service bug, re-test after mantle deployments — a server-side fix would flip gpt-5.4/5.5 from uncacheable to fully cacheable with zero bound changes. Diagnose with the agent harness's `cache` diagnostic (`--dump-wire` now also writes `unmatched-N.json` for unclassified wires) or the raw replay probe; warm-turn `tokens_cache_read` in the `turns` table is the production signal for whether breakpoints are landing.

### Encrypted reasoning is bound to the provider that minted it

Opaque OpenAI-Responses encrypted reasoning (`reasoning_encrypted_content`, returned under `store: false`) only decrypts on the exact provider endpoint that minted it. One `model_backends` id can be served by more than one provider: `gpt-5.6-sol`, for example, is served on one host by Bedrock Mantle (`provider_mode: openai_responses`, a regional Mantle deployment) and on another host by the ChatGPT/Codex backend (`chatgpt-oauth`), which does not use Mantle at all. GitHub Copilot's Responses route (`github-copilot`) is a third minting surface. Each mints encrypted reasoning only it can decrypt. The agent loop runs on the trigger host and relays each inference call to whichever host currently serves the model, so a thread whose turn N ran on provider A and turn N+1 on provider B replays A's encrypted blob into B — which rejects the whole request with `invalid encrypted reasoning` / `The encrypted content rsn_... could not be verified. Reason: Encrypted content could not be decrypted or parsed.` / `encrypted content missing recognized prefix`. The rejection fires in both directions (Mantle rejects Codex blobs, Codex rejects Mantle blobs) and the wording varies by endpoint; all phrasings mean the same thing. Do NOT infer the minting provider from the blob's text or prefix — the prefix is not a reliable identity marker. Same-provider consecutive turns always succeed; the signature is an `error` turn that follows an `ok` turn relayed to a DIFFERENT provider/host.

Two layers defend against this, both in `packages/llm`, shared across every driver that mints and replays OpenAI-Responses encrypted reasoning (`bedrock-mantle`, `chatgpt-oauth`, `github-copilot`'s Responses route). (1) Provenance: a thinking block that carries `reasoning_encrypted_content` is stamped with a `reasoning_origin` key at mint time. The key is built by `buildReasoningOrigin` (`drivers/shared.ts`) as `${siteId}:${provider}[:${detail}]` — `siteId` distinguishes two hosts serving the same provider, `provider` distinguishes two providers on one host, and the optional `detail` (region + provider mode on Mantle) distinguishes a provider that mints un-cross-decryptable blobs from more than one endpoint on the same host. The stamp is emitted on the `reasoning-end` stream chunk (`bridge/stream.ts`), captured by the stream parser, stitched onto the assembled block (`buildAssistantToolCallBlocks`), and carried across the relay (`reasoning_origin` on `streamChunkPayloadSchema` / `wsStreamChunkSchema`). At request-build time the executing driver passes its own `reasoningOrigin` into `toModelMessages`; `buildReasoningPart` (`bridge/messages.ts`) drops the encrypted content of any block whose `reasoning_origin` differs from the executing deployment's. The drop decision lives where the executing deployment identity is known (the driver on the host that will run the request), NOT on the loop host. Unstamped legacy blocks have no origin to compare, so they are kept and lean on layer 2. (2) Recovery: when the provider rejects a request with one of the encrypted-reasoning errors above (`isEncryptedReasoningRejection` in `bridge/request-diagnostics.ts`, matched on phrasing — never on blob prefix), the shared `withEncryptedReasoningRetry` wrapper (`drivers/shared.ts`) reissues exactly once with ALL encrypted reasoning stripped from the replayed history (`stripEncryptedReasoning` option), so legacy and unforeseen cases self-heal instead of failing the task. The matcher is narrow (only those phrases) and the retry is single; any other error, and a second encrypted-reasoning rejection, propagates. The reasoning text is empty on these turns, so dropping the blob costs nothing but the un-replayable state — the inline text and tool calls in the same assistant message still replay.



The native `@ai-sdk/openai` Responses driver defaults `reasoning.summary` to `"detailed"` on any request it treats as a reasoning model that also carries a non-`none` effort — the caller need never set it. Its `resolvedReasoningSummary` is `openaiOptions.reasoningSummary !== undefined ? openaiOptions.reasoningSummary : (effort != null && effort !== "none" ? "detailed" : undefined)`, and `summary` rides the wire body whenever it resolves non-null (`openai-responses-language-model`). The Mantle driver supplies both trigger conditions: `buildMantleOpenAIOptions` (`packages/llm/src/drivers/bedrock-mantle.ts`) sets `forceReasoning: true` (Mantle's `openai.` ids bypass the SDK's id-based reasoning detection, so this is required for effort to reach the model at all) and maps an effort. The Bedrock-Mantle Responses endpoint rejects the field with `400 Unsupported parameter: 'reasoning.summary'` — it replays encrypted reasoning, not summaries. This surfaced as bug #272: every effort-bearing GPT-5.x-on-Mantle turn 400'd, including aux-dispatch traffic on `openai.gpt-5.6-*`, and looked like a model-switch leak because *each* Mantle turn trips the default independently — the prior model is a red herring. The fix pins `reasoningSummary: null` in `buildMantleOpenAIOptions`. `null`, not `undefined`: the SDK checks `!== undefined` and the schema is `.nullish()`, so `null` takes the explicit branch and drops `summary` from the body, while `undefined` falls back into the `"detailed"` default. A thinking-disabled turn maps effort `"none"`, which already suppresses the summary, but the driver pins `null` unconditionally so an SDK-gate change can't reopen the trap.

### OpenAI-compatible providers never report cache-write tokens

On every model served by an OpenAI-compatible endpoint (glm, kimi, deepseek, …), `turns.tokens_cache_write` stays NULL turn after turn while `tokens_cache_read` populates densely; on `chatgpt-oauth` models it reads 0. NULL there means *the upstream response carried no cache-write counter for bound to map* — it does not mean no cache write occurred. The usage bridge (`packages/llm/src/bridge/stream.ts`) maps every write counter that exists on a response — `usage.inputTokenDetails.cacheWriteTokens` (provider-agnostic), `providerMetadata.bedrock.usage.cacheWriteInputTokens`, and `providerMetadata.anthropic.cacheCreationInputTokens` — but OpenAI-compatible chat-completions endpoints report only `prompt_tokens_details.cached_tokens` (a read counter), and the Codex/Responses path never reports a nonzero write count either — zero on every observed turn, including turns reading six-figure cache totals. The same bridge code populates `tokens_cache_write` densely for Bedrock and Anthropic models, which is the proof the gap lives upstream, not in the bridge.

Diagnostic rule: never treat NULL/0 `tokens_cache_write` on an OpenAI-compatible model as evidence of a caching defect — it carries no signal (it once sent an astra cache investigation chasing a nonexistent defect across two stranded probe dispatches). Measure cache effectiveness on these models from `tokens_cache_read` alone: consecutive warm turns reporting the same large cached figure on a shared prefix are definitive hits. The column will not populate short of an upstream wire change; if an endpoint starts emitting a write counter, the bridge picks it up automatically.

### Importing a package can create logs/bound.log in cwd

`createLogger()` (in `packages/shared/src/logger.ts`) is not side-effect-free: the first call materializes the pino root, which `mkdirSync`s `logs/` and opens `logs/bound.log` under `process.cwd()` **synchronously** (since `571be0f6`). Any module that calls `createLogger()` at module scope therefore writes a log file into whatever directory the *importing process* happens to run from — not just when that process is bound itself.

This bit `boundless`: `packages/llm/src/bridge/stream.ts` used to call `createLogger("llm", "ai-sdk-bridge")` at module scope, and `@bound/llm`'s index re-exports the bridge, so merely importing `@bound/llm` (which boundless does for image-budget constants like `PROVIDER_IMAGE_RAW_MAX_BYTES`) dropped a 0-byte `logs/bound.log` into boundless's cwd on every launch. It was empty because boundless never logs through pino — it has its own `AppLogger` under `~/.bound/less/logs/` — and the bridge logger only fires on a streamed tool_use anomaly the TUI never hits. The symptom looked Windows-only (that's where it was noticed; `logs/` is gitignored so git never flagged it), but the mechanism is platform-independent — it happens on macOS/Linux too.

Rule: never call `createLogger()` at module scope in a module reachable by just importing a package. This is the same reason `packages/cli/src/bound-main.ts` lazy-imports the start subtree (see its header comment). If a logger fires only in rare paths, make it lazy — `let logger: Logger | null = null;` + a `getLogger()` that calls `createLogger()` on first use — so the file appears only when a log line is actually warranted. Regression test: `packages/llm/src/__tests__/import-side-effect.test.ts` imports the package index from a temp cwd in a fresh process and asserts no `logs/bound.log` appears.

### Yard's `input` can arrive as JSON text, not a value

`yard`'s `input` param is `z.any()`, so a **string** passes validation. Models routinely emit nested object params as JSON *text* rather than a nested object (same class as the tavily list-arg serialization), and the driver's marshalling is faithful in both directions: `runYardProgram` does `JSON.stringify(options.input)` on the host side (`packages/agent/src/yard/driver.ts`) and the guest bootstrap does `JSON.parse(json)` before `deepFreeze`. Stringify-then-parse of a *string* round-trips back to the same string, so the guest receives `typeof input === "string"`, `Object.keys(input)` returns character indices (`["0","1","2",...]`), and every `input.field` is `undefined`. Observed live: a program calling `aux(name, input.riskQuestion)` failed with `tool() args must be JSON-compatible (found undefined)` — an accurate error pointing one level away from the cause, which invites debugging the guest program instead of the boundary. The tell is that the received string's whitespace matches the literal tool-call text (`{"alpha": 1, ...` with spaces), since `JSON.stringify` never emits spaces.

**Fix (`normalizeYardInput` in `packages/agent/src/tools/yard.ts`, applied at the `runYardProgram` hand-off):** a string `input` whose trimmed form starts with `{` or `[` and parses to an object/array is decoded before being handed to the driver. Scalar strings are passed through untouched — `"hello"`, `"42"`, and `"true"` are legitimate input values, so the recovery cannot swallow a deliberate string payload. The narrow object/array gate is what makes the coercion safe; widening it to all parseable JSON would turn `input: "42"` into a number.

### `bun install` under the boundless sandbox writes its caches to tmpdir

`boundless_bash` confines writes to the working directory, the temp directory, and `/tmp`. Three parts of a plain `bun install` in this repo write outside those roots, and each one is handled where it happens, so a sandboxed `bun install` / `bun add` works with a cold cache and no caller env:

- **bun's global install cache.** bun stages every download in `~/.bun/install/cache` before linking into `node_modules`. Unconfined, the install dies with `error: bun is unable to write files to tempdir: PermissionDenied` — the message misdirects, since the failing write is the cache dir's and `TMPDIR` is irrelevant.
- **node-gyp's header devdir.** The root `postinstall` builds `tree-sitter-kotlin` with node-gyp, which downloads Node headers into `~/Library/Caches/node-gyp` (macOS) or `~/.cache/node-gyp` (Linux) and fails with `EPERM: operation not permitted, mkdir`.
- **The root `prepare` hook.** It sets `core.hooksPath`, and the sandbox keeps `.git/config` read-only on purpose; `git config` exits 4 (`could not write config file`).

`spawnSandboxed` (`packages/less/src/tools/sandbox.ts`, seatbelt and bubblewrap) passes `nonInteractiveEnv({ confineInstallCaches: true })`, which sets `BUN_INSTALL_CACHE_DIR=<tmpdir>/bound-bun-install-cache` and `npm_config_devdir=<tmpdir>/bound-node-gyp` unless the operator already set them (either spelling of the devdir variable counts). Unsandboxed spawns keep the warm home-directory caches. The Windows lowbox path (`spawnLowbox`) inherits the host environment and does not apply this confinement.

`prepare` runs `scripts/install-git-hooks.ts`: it skips the write when `git config --get core.hooksPath` already reads `.githooks`, writes it otherwise, and prints a warning instead of failing the install when git refuses the write. A normal clone gets its hooks on the first `bun install`; a clone first installed inside the sandbox prints the warning and needs one `git config core.hooksPath .githooks` outside it. The `.git/config` protection stays as it is.

The bun cache confinement had been in place since `ef67060f`, and a sandboxed shell sees `BUN_INSTALL_CACHE_DIR` set and writable. Installs that still failed were dying in the node-gyp build (exit 1) and the `prepare` hook (exit 4), so a manual `BUN_INSTALL_CACHE_DIR` override did nothing for them.

Installed packages are ordinary files (hardlink count 1), so a cleared tmp cache never breaks an existing `node_modules`. One follow-up is still on the caller: commit the `bun.lock` change alongside the `package.json` change. An aux arm that installed the tree-sitter grammars without updating the lock broke `bun install --frozen-lockfile` (CI's install step) on pristine checkouts until `0a8fc7a8`.

### Dependency lifecycle scripts that call node-gyp race the isolated linker

Bun's isolated linker (the default for this workspace) runs a trusted dependency's `preinstall`/`install`/`postinstall` script **while it is still linking other packages**. A script that builds a native addon with `node-gyp` needs node-gyp's own runtime dependencies (`tar`, `env-paths`, `nopt`) already symlinked into `node_modules` — but on a cold cache they may not be yet, so the build dies with `gyp ERR! stack Error: Cannot find module 'tar'` and `bun install --frozen-lockfile` fails intermittently. It is a race: a warm cache, or a second install with the dependencies already in place, succeeds, which is why it only showed up on cold-cache CI/release runs (release run 45222779309; CI runs 44634982514 / 44642575960).

`tree-sitter-kotlin@0.3.8` is the package that bit us: it ships **no prebuilds**, so its `install: node-gyp-build` script falls through to `node-gyp rebuild`, and it is in **Bun's default-trusted list** (`bun pm default-trusted`, 367 entries), so Bun runs that script at link time. Every other Tree-sitter grammar ships `linux`/`darwin`/`win32` prebuilds, so `node-gyp-build` resolves a prebuild and never invokes node-gyp during linking.

The fix is to keep any node-gyp-invoking script out of the link phase, not to retry the install. With **no** `trustedDependencies` field, Bun uses its default-trusted list; declaring an explicit `trustedDependencies` array **replaces** that list entirely (verified on Bun 1.4.5), so a scripted dependency not named in it has its lifecycle script blocked. The root `package.json` lists the rest of the currently-running set (`esbuild`, `node-pty`, `sharp`, `tree-sitter`, `tree-sitter-cli`) and omits `tree-sitter-kotlin`; kotlin's native addon is built from the root `postinstall` instead (`scripts/build-tree-sitter-kotlin.ts`), which Bun runs only **after** every dependency is linked — so node-gyp's own dependencies exist by then and the build cannot race. `scripts/validate-kotlin-not-link-built.ts` (wired into `bun check`) guards both halves of the invariant. If you add another native dependency whose install script shells out to node-gyp and ships no prebuild for the install host, either add a prebuild path or move its build into the root postinstall the same way — do not add it to `trustedDependencies`, and do not paper over the race with `|| bun install`.

### `bun --cwd <pkg> run <script>` silently no-ops

Bun's `--cwd` flag must come **after** `run`: `bun run --cwd packages/docs check` executes the script. The reversed form `bun --cwd packages/docs run check` (bun 1.3.14) prints bun's own `bun run` usage text and exits **0** without executing anything — a validation command that always reports success, which is worse than no validation at all.

Observed live: CONTRIBUTING.md documented the reversed form as the docs check command until `fc6a10cc`. A docs release ran the documented command as its pre-push validation, saw exit 0, and shipped a Markdown lint failure to CI (`289a184b`'s Docs workflow red — MD012, caught only because the operator watched the Actions page). When a "check" command produces no check output — no lint progress, no build lines, just usage text — treat the silence as the failure.

### Tool-result content items must match ai@7's prompt schema

The bridge's `buildToolResultOutput` (`packages/llm/src/bridge/messages.ts`) emits image/document blocks riding in a `tool_result` as `output: { type: "content", value: [...] }`. In ai@7 those value items MUST be canonical file items with tagged inline data — `{ type: "file", data: { type: "data", data }, mediaType }`. The ai@6-era `{ type: "media", data, mediaType }` item is not in ai@7's `ModelMessage[]` prompt schema, and `validatePrompt` rejects the entire prompt on one unknown item (`Invalid prompt: The messages do not match the ModelMessage[] schema.`). The failure fires inside `generateText` before any provider call, so it is model-independent — switching models changes nothing — and because the offending block lives in persisted `messages.content`, every subsequent assembly re-converts it and re-fails. Before the prompt-schema guard below, that wedged the thread until someone edited the DB.

Observed live (thread `10e34ac9`, 2026-10-10): a `boundless_read` on a JPEG returned an `image` block inside the tool_result — the first image-bearing tool_result in that thread's history — and the very next request died with the schema error. Three consecutive alerts across `glm-5.3-flash` and `opus` (including a non-vision model, which is why the trail initially read as a vision-capability bug) before the actual locus surfaced in the bridge layer.

Two schema subtleties worth keeping in hand when touching this code. First, the SDK's `outputSchema` is position-sensitive: the user/assistant `filePartSchema` accepts bare `string | Uint8Array | ArrayBuffer` inline data, but tool-result content items require the tagged discriminated union (`{ type: "data" | "url" | "reference" | "text", ... }`) — a bare string is valid one schema up and fatal here. Second, downstream mapping differs per adapter: `@ai-sdk/anthropic` converts `image/*` items into base64 image blocks (and `application/pdf` into a PDF document block, enabling the `pdfs-2024-09-25` beta) inside the Anthropic `tool_result` content, while `@ai-sdk/openai-compatible` JSON-stringifies the whole value array into the tool message string, so a `file` item there would reach the model as base64 text, re-sent on every later turn. The OpenAI-compatible driver and OpenCode Go's chat-completions leg therefore pass `toolResultMedia: "text-only"` to `toModelMessages`: each tool-result image becomes an `[Image omitted: file_id=… media_type=… reason="provider takes text-only tool results"]` placeholder and each document its `text_representation` (or the document-unavailable placeholder), with text items and order kept. Anthropic, Bedrock, Mantle, ChatGPT OAuth, and Copilot keep `file` items, so images in tool results stay model-visible there.

Runtime guard: the last step of `toModelMessages` (`guardPromptSchema`) checks each message against ai's `modelMessageSchema`. A valid message comes back as the same object. In an invalid one, each content part or tool-result `output.value` item that fails is replaced with `[Unsupported <type> content omitted: it does not match the model prompt schema]`, keeping tool-call ids and call/result pairing, and the bridge logs one warning per replacement (message index, role, item type; never content). The placeholder depends only on the item's `type`, so the same history yields the same prompt bytes and the prompt-cache prefix holds. A drifted persisted item now costs that one item, not the thread. Don't treat the guard as license to emit new shapes: a warning from it is a bridge bug to fix.

Test guards: `packages/llm/src/__tests__/ai-sdk-bridge.test.ts` drives the real validator — `generateText` + `MockLanguageModelV4` — with one test asserting bridge output passes prompt validation and a control asserting the raw legacy `media` item still fails it; `prompt-schema-guard.test.ts` pins the repair, and `packages/agent/src/__tests__/agent-loop-prompt-guard.test.ts` runs a full turn through a real driver over a thread holding a drifted tool_result.

### Bun coverage thresholds are per-file, `--parallel` under-reports, and 1.4.0 over-reports

Three Bun 1.4 behaviors make `bunfig.toml` unusable as a package coverage gate:

- `coverageThreshold` keys are `lines` and `functions`. The singular `line` / `function` are ignored without a warning, so a misspelled threshold enforces nothing. bunfig carried `{ line = 0.6, function = 0.6 }` until the coverage ratchet replaced it: `packages/shared` passed it at 0.99 while its package total sat at 79% functions.
- Spelled correctly, the threshold applies to every file, not the package total. One 0%-function helper (`packages/shared/src/assert.ts`) fails the package at `lines = 0.01`.
- A `bunfig.toml` inside `packages/<pkg>/` is read only when `bun test` runs from that directory. CI and the pre-commit gate run `bun test packages/<pkg>` from the root, so package-level thresholds never fire.

Bun 1.4.0 over-reports line coverage: its hit counts are wrong and it credits lines that never ran. A five-line function called 1,000 times reported hits of 12 and 21 and credited its closing brace; in `packages/sync/src/ws-transport.ts` it credited the frame-splitting branch of `encodeChangelogFrames`, which no test reaches. The same 491 sync tests measured 93.2% lines under 1.4.0 and 83.9% under 1.4.5. Measure with the Bun version CI pins (`bun-version` in `.github/workflows/ci.yml`, currently 1.4.5); floors written from a 1.4.0 run fail CI.

Separately, `bun test --parallel` reports coverage for only part of the executed code. Same tests, same exit code: `packages/core` measured 71.3% lines under `--parallel` and 85.0% serially. Measure coverage serially.

`scripts/validate-coverage.ts` sums each package's lcov report and holds the total at its floor in `scripts/coverage-baseline.json`.

Bun's lcov report also omits every file no test imports, so an untested file is invisible rather than 0%. The ratchet adds those files back at 0% with line and function counts estimated from the transpiled source, which keeps a package's first test for an untested file from lowering its total. Unloaded `.svelte` components are compiled and estimated the same way.

### `.svelte` imports under `bun test` need the preloaded svelte plugin

Bun has no `.svelte` loader: without one, `import Btn from "./Btn.svelte"` resolves to the file's path string. The import succeeds, `expect(module).toBeDefined()` passes, and no component code runs, so coverage never sees the file. `scripts/svelte-test-plugin.ts` (preloaded by `scripts/test-preload.ts`) compiles each component with `generate: "client"`, as the Vite build does.

The plugin also redirects svelte's server entry points to the browser builds. Bun's test runner resolves the package exports' `default` condition (`index-server.js`), where `mount` throws `lifecycle_function_unavailable`; Vite resolves `browser`. See `packages/web/src/client/__tests__/render-btn.test.ts` for mounting a component under jsdom.

Mount through `installDom()` in `packages/web/src/client/__tests__/harness/dom.ts`, never a private `new JSDOM()`. svelte's client runtime caches `window`, `document` and the Node/Element prototype getters the first time it renders (`init_operations`) and never re-reads them, so a second window breaks every later component test in the process with `undefined is not an object (evaluating 'Element.prototype')`. The harness keeps one window per process and resets it between files. For the same reason, prefer `spyOn(moduleNamespace, "fn")` over `mock.module()` in component tests: `mock.module` replaces the module for the whole process and breaks that module's own tests in later files.

The plugin also compiles runes modules (`.svelte.js` / `.svelte.ts`) with `compileModule`. @xyflow/svelte ships its stores that way; uncompiled, they throw `rune_outside_svelte` at import.

Bun attributes a compiled component's coverage to its `.svelte` path without applying the inline source map: line numbers in the coverage report are lines of the compiled JS, not the `.svelte` source. Totals and percentages are real. To read an uncovered range, compile the component (`compileSvelteModule`) and look up those lines in the output.

### Never construct a just-bash `Bash` outside `createSandbox`

just-bash 2.14.4 normalizes every script by `trimStart()`-ing each non-heredoc line, without tracking quotes, unless `ExecOptions.rawScript` is `true`. A quoted multiline argument loses its indentation: `python3 -c` bodies fail with `IndentationError`, and whitespace-sensitive literals are rewritten while the command exits 0 (#308).

`createSandbox` in `packages/sandbox/src/sandbox-factory.ts` is the exec seam: it returns a `Bash` subclass that forces `rawScript: true` on every `exec`, including nested `bash -c` and `source`. Get the shell from `createSandbox`, pass options straight through, and never write `new Bash(` or `rawScript` in `packages/*/src`. `scripts/validate-sandbox-exec-seam.ts` fails `bun check` on either. Tests may build a raw `Bash` to probe just-bash itself, but a test that stands in for the production sandbox should build it with `createSandbox`.
