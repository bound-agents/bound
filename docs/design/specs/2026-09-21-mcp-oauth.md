# RFC: MCP OAuth Authorization

**Supplements:** `2026-05-08-mcp-platform-connectors.md`; `2026-08-31-durable-work-consolidation.md` (durable_work spool); `2026-06-29-unified-delegation.md` (R-UD12 tool relay)
**Date:** 2026-09-21
**Status:** Draft
**Prerequisite:** MCP TypeScript SDK v2 package split (commit `b85b5615`)

---

## 1. Problem Statement

An `http` MCP server can require the caller to hold an OAuth access token. Bound today offers one authentication path for such servers: a static `Authorization` header configured in `mcp.json`. That path serves pre-issued long-lived tokens and nothing else. A server that returns `401 Unauthorized` with a `WWW-Authenticate` challenge, advertises a protected-resource metadata document, or steps up scope mid-session (`403 insufficient_scope`) cannot be authenticated at all — the MCP call fails and the server is dead to the cluster.

The standard remedy is the OAuth 2.1 authorization-code flow with PKCE, as profiled by the MCP authorization specification: the client discovers the resource's authorization server, registers, redirects a browser to the authorization endpoint for operator consent, catches the callback, and exchanges the resulting code for a token. That flow assumes a single machine that is simultaneously the MCP caller, the holder of the browser, and the custodian of the resulting token.

Bound is a cluster. The host that owns an MCP server config, the host running the agent loop that issued the failing tool call, and the machine in front of the operator who must click "allow" are frequently three different hosts. A grant obtained on one must serve MCP calls on another without the token ever leaving its custodian. The consent step takes minutes of human wall-clock time and must not pin a relay request open across it.

This RFC defines how bound obtains, custodies, and applies OAuth grants for `http` MCP servers across the cluster.

## 2. Architectural Frame

Bound implements the **third-party authorization flow** from MCP authorization revision 2025-03-26 (§"Third-Party Authorization Flow", <https://modelcontextprotocol.io/specification/2025-03-26/basic/authorization#third-party-authorization-flow>) internally. In the reference flow an MCP server sits between the MCP client and a third-party authorization server: it acts as an OAuth **client** toward the upstream authorization server and as an OAuth **authority** toward the MCP client, binding the two sessions and minting its own downstream token.

Bound casts the **host that owns an MCP server config** in that dual role. Toward the upstream authorization server it is a plain OAuth client. Toward the rest of the cluster it is the authority that owns the resulting grant. The reference flow's downstream half — where the authority mints and validates its own bearer token for its own clients — is **replaced** by bound's existing Ed25519-authenticated `durable_work` relay. The session binding is not a minted token; it is a token-fenced `durable_work` claim on the owning host.

Three deviations from the reference flow are load-bearing and named here so the reviewer's referent is fixed:

1. **No downstream token is ever minted.** The reference authority issues its clients a bearer token that stands in for the upstream grant. Bound issues nothing. Cross-host access to an MCP tool is the tool call itself relaying to the owning host (R-UD12), authenticated by the transport's per-peer Ed25519 keys. The grant is applied only where it is held.
2. **The OAuth callback lands on the resolving host, not the owning host.** Consent happens in front of whatever operator is present, on whatever machine holds the browser. That machine catches the redirect. In the reference flow the authority that will hold the token also catches the callback; here those are decoupled.
3. **Only a single-use authorization code and its PKCE verifier cross the relay — never a token.** The resolving host obtains the code and hands it, with the verifier, to the owning host over one `durable_work` hop. The owning host performs the code-for-token exchange with its own client credentials. No access or refresh token is ever transmitted between hosts.

At the external wire — the upstream MCP server and its authorization server — bound is a plain conformant OAuth client per the **current MCP authorization specification**: authorization-code grant with PKCE (RFC 7636), protected-resource-metadata discovery (RFC 9728), authorization-server-metadata discovery (RFC 8414), and the resource indicator (RFC 8707) on both authorize and token requests. Conformance targets the latest published revision, not a pinned one: the authorization mechanics are governed by the underlying OAuth RFC stack, which the MCP specification profiles rather than redefines, and revisions to date have refined that profile without breaking it — so a client tracking the latest revision interoperates with servers written against earlier ones.

The 2025-06-18 revision **removed** the third-party section. Its removal was motivated by two hazards: an authority minting and validating its own downstream tokens (a second bearer artifact to leak, revoke, and rotate) and confused-deputy exposure when the authority brokers for arbitrary, mutually-distrusting third-party clients. Both are structurally absent here. The trust domain is closed: every host is a single operator's Ed25519-keyed node, already in every peer's trusted computing base for change-log replication and relay. No downstream bearer artifact exists to leak. There are no arbitrary third-party clients — the only "clients" of the authority are the operator's own hosts, reaching it over authenticated relay. The pattern bound adopts is the reference flow's *shape* applied inside a closed cluster, not its hazardous *generalization* to an open broker.

## 3. Scope and Non-Goals

### 3.1 In scope

OAuth authorization-code + PKCE authentication for `http` MCP servers: config surface, per-authorization-server client identity resolution, the synced challenge that carries an unmet authorization demand, the raise path from a `401`/`403`, agent-loop suspension while consent is pending, cluster-wide resolution through any host or the CLI, per-host token custody, and the operator surfaces on which consent is requested.

### 3.2 Non-Goals

- This RFC does **not** alter the static-`headers` bearer path. A configured `Authorization` header remains a supported, unchanged way to authenticate an `http` MCP server.
- This RFC does **not** authenticate `stdio` MCP servers. OAuth applies to the `http` transport only.
- This RFC does **not** mint, validate, sync, or relay any bearer token. Tokens are per-host files (§9).
- This RFC does **not** add a token-expiry or challenge-expiry clock of bound's own. Authorization codes and consent grants are the authorization server's to expire (§6).
- This RFC does **not** establish direct spoke-to-spoke transport. The code+verifier handoff rides the existing hub-mediated `durable_work` relay.

## 4. Configuration

The `http` MCP server entry in `mcpSchema` (`packages/shared/src/config-schemas.ts`, `transport: z.literal("http")` at the strict-mode union member) gains an optional `auth` block. The mirror union `McpServerConfig` on the less side (`packages/less/src/mcp/manager.ts`) carries the same shape so the terminal client's MCP bridge sees identical config.

```ts
auth?: {
  type: "oauth";
  scopes?: string[];        // requested scope set; the AS is authoritative on grant
  client_id?: string;       // pre-registered client, or a CIMD https-URL client_id
  client_secret?: string;   // confidential-client secret; owner-host config only
};
```

**R-MO1.** The `http` MCP server schema shall accept an optional `auth` block of `type: "oauth"` with optional `scopes`, `client_id`, and `client_secret` fields, declared in strict mode in both `mcpSchema` and the less-side `McpServerConfig` union. Its absence shall leave the server on the existing static-`headers` path.

**R-MO2.** The existing `headers` field shall remain unchanged and shall remain the static-bearer path. When an `auth` block is present and a token has been obtained, the v2 SDK `OAuthClientProvider` supplies the `Authorization` header and, per v2 header precedence, a provider-held token outranks a configured `Authorization` header. A configured header therefore serves as a fallback that applies only until a provider token exists.

**R-MO3.** `client_id` shall be treated as non-secret. It may appear in synced challenge rows (§5). A Client-ID-Metadata-Document (CIMD) `client_id` is an https URL carried verbatim in this same field; CIMD requires nothing client-side beyond supplying that URL as the `client_id`.

**R-MO4.** `client_secret` shall be treated as a secret. It shall be declared only in the **owning host's** config, shall never be written to a synced row, and shall never cross the relay in a challenge row or a `durable_work` handoff. This mirrors the existing treatment of the Discord token in `platforms.json`: an owner-host secret that never replicates.

**R-MO5.** `mcp.json` shall remain operator intent. Machine-written authorization state — client registrations and token bundles — shall live beside it under `config/mcp-auth/`, not inside `mcp.json`.

## 5. Challenge Table

Authorization state that must be actionable from every surface is a synced row. The row carries the **demand** — what authorization is unmet — not a consent URL, because the URL is minted freshly per resolution attempt (§6) and is resolver-local.

**R-MO6.** The system shall define a synced LWW table (`mcp_auth_challenges`) recording an unmet authorization demand. Each row shall carry: the MCP server name, the owning `site_id`, the MCP server URL, the scope demand parsed from the `401`/`403`, the `resource_metadata` hint if the challenge advertised one, the config-declared `client_id` if any, and a `status` of `pending → resolved | failed`, plus the standard synced-table columns (`deleted`, `modified_at`, and the deterministic-id and LWW conventions).

**R-MO7.** A challenge row shall carry **no secret**: no `client_secret`, no PKCE verifier, no authorization code, no token. The fields a challenge carries are those safe to replicate to every host.

**R-MO8.** The challenge table shall have **no expiry or TTL column**. Staleness is authorization-server-owned: authorization codes are single-use and minutes-lived, and each resolution attempt (§6) mints fresh PKCE, so an abandoned consent dies at the authorization server rather than under a bound timer. Terminal outcomes are driven by the exchange result — the v2 SDK `OAuthError` / `OAuthClientFlowError` taxonomy maps an authorization-server response to a `status` transition. A row reaches `failed` on a terminal authorization-server rejection and `resolved` on a successful exchange; a row otherwise remains `pending` and re-resolvable.

**R-MO9.** The challenge table shall satisfy the "Adding a new synced table" checklist as end state: it shall be a STRICT table declared in `packages/core/src/schema.ts`; it shall appear in `SyncedTableName` and `TABLE_REDUCER_MAP` (`packages/shared/src/types.ts`) with an `lww` reducer; it shall have a repository module under `packages/core/src/repositories/` with no inline reads in feature code; it shall appear in `SYNCED_TABLE_NAMES` (`packages/core/src/schema-introspection.ts`); and it shall appear in `SNAPSHOT_TABLE_ORDER` (`packages/sync/src/ws-transport.ts`). A row's non-`id` primary key, if any, shall be registered in `TABLE_PK_COLUMN`.

The rationale for syncing the challenge while keeping tokens per-host: a challenge must be **visible and actionable** from every surface and every host — the operator may sit at any node — whereas a token must be **held in exactly one place** so that exchange and refresh always use one client identity (§9).

## 6. Raise Path

**R-MO10.** When an MCP call on the owning host receives `401 UnauthorizedError` or `403 insufficient_scope` (the SEP-2350 step-up case), the v2 `OAuthClientProvider`'s `redirectToAuthorization` seam shall raise a challenge row (§5) rather than drive a browser redirect in place. The provider does not itself open a browser; it records the demand and returns control.

**R-MO11.** When the failing call arrived over the relay, its execution shall return a typed `auth_challenge_raised` tool outcome immediately, naming the challenge id. A relayed request shall **never** dangle open across the minutes-long consent step. The requester's loop parks on the challenge (§7); the relay request settles at once.

**R-MO12.** A refresh failure at the authorization server (an expired or revoked refresh token) shall raise a fresh challenge rather than fail the call silently. This is the reference flow's "invalidate downstream sessions when the third-party token expires," translated: the grant is gone, so a new consent is demanded.

**R-MO13.** A startup or connect-time authentication failure for one MCP server shall mark that server unauthenticated and shall not fail the MCP bridge or host startup. Other servers remain available; the unauthenticated server raises a challenge on first use.

---

## 7. Suspension

**R-MO14.** The requester's agent loop shall park the pending MCP tool call as a loop suspension in the same family as client tools (invariant #21 shape). No tool result shall be persisted while the call is suspended (invariant #7 remains intact — nothing reaches the next LLM call mid-suspension). The consent affordance shall be surfaced on the active surface (§8), and the suspension shall wait on the challenge row.

**R-MO15.** Resolution shall flip the synced challenge row and wake the suspended loop through an event of shape `mcp:auth:<challengeId>`, mirroring `connector:event:<handleId>`. The wake shall re-dispatch the **identical** MCP call. Re-dispatch is safe because a `401`/`403` refused the request before any server-side effect occurred; the retried call is the first that can succeed.

**R-MO16.** The suspension shall carry **no bespoke timer**. It rides session lifecycle exactly as client tools do. If the session ends before the challenge resolves, the call shall settle with an actionable error naming the challenge id and the CLI command that resolves it (§8d). The challenge row survives session end and remains resolvable.

## 8. Resolution

Resolution separates two roles: the **resolver** is the consent front-end (it owns the browser and catches the callback); the **owner** is the token custodian (it holds the client credentials and performs the exchange). They may be the same host or two hosts.

**R-MO17.** Any host, and the CLI on any machine, shall be able to claim a `pending` challenge. On claiming, the resolver shall:

1. **Re-run discovery live** against the resource and its authorization server — RFC 9728 protected-resource metadata, then RFC 8414 authorization-server metadata. Discovery is performed at resolution time; no snapshot in the challenge row is trusted as current.
2. **Resolve client identity** per the registration ladder (§10) for this authorization server.
3. **Mint fresh PKCE and `state`.**
4. **Build the authorize URL** with `redirect_uri` pointing at the **resolver's own** localhost web router. The web router (port 3001) is localhost-only — only the sync router is exposed beyond the host — so the callback must land where the browser is, which is why the resolver, not the owner, catches it.
5. **Open or surface** the authorize URL on the active surface (§8).
6. **Catch** `GET /oauth/mcp/callback` on the resolver's web router — a new Hono route module following the existing `packages/web/src/server/routes/` pattern (registered in `routes/index.ts` beside the other `create*Routes` mounts). The route shall clear the DNS-rebinding Host guard applied at the web server boundary (`packages/web/src/server/start.ts`).
7. **Correlate** the callback to the challenge by `state`.
8. **Never exchange the code.**

**R-MO18.** Resolver-local ephemera — PKCE `state`, PKCE verifier, and live discovery state — shall be **provider-local**, held through the v2 `saveCodeVerifier`/`saveDiscoveryState` seams, and shall never sync. They exist only for the duration of one resolution attempt on the resolving host.

**R-MO19.** Having caught and correlated the code, the resolver shall write a **peer-targeted `durable_work` handoff** to the owning host carrying: the authorization code, the PKCE verifier, the `redirect_uri` used, the `issuer`, and the registration used (a config-declared `client_id` or the DCR result). The handoff shall **never** carry `client_secret` — the owner already holds it (R-MO4). A self-owned challenge shall use `LOCAL_WORK_TARGET` and consume the handoff in-process with no peer hop.

**R-MO20.** The owner shall consume the handoff **exactly once** under a token-fenced claim on its local `durable_work` lane (invariant #3). It shall perform the code-for-token exchange at the token endpoint using its own client credentials. The `redirect_uri` in the token request is validated by the authorization server by **string equality**, not by reachability — the owner's exchange succeeds against a `redirect_uri` that named the resolver's loopback, because the AS compares the string it saw at `/authorize`. On success the owner shall store the token bundle (§9) and flip the challenge row to `resolved`.

**R-MO21.** Because the exchange and every subsequent refresh run only on the owner with the owner's single client identity, there shall be exactly one client identity for a given (host, authorization server) pair, held in one place. A dead or already-consumed authorization code fails the exchange at the authorization server; the owner shall mark the challenge `failed` and a subsequent use raises a fresh challenge. The authorization code's own single-use, minutes-lived nature bounds the handoff — no bound-side timer is needed to expire it.

## 9. Token Custody

**R-MO22.** Tokens shall be held in per-host bundle files at `config/mcp-auth/<server>.json`, modeled on the ChatGPT-OAuth `FileTokenStore` / `TokenManager` (`packages/llm/src/drivers/chatgpt-oauth/token-store.ts`): expiry-gated access, single-flight refresh (concurrent expiry checks share one refresh POST), and rotated-bundle-persisted-before-return (a refresh response that rotates the refresh token is written to disk before the new access token is handed to any caller).

**R-MO23.** The v2 `OAuthClientProvider` implementation shall honor these contract points: implement `discoveryState()` / `saveDiscoveryState()`; round-trip the SEP-2352 issuer stamp verbatim; and propagate `saveTokens()` failures rather than swallowing them (a persistence failure must not leave an in-memory token the disk does not have).

**R-MO24.** Tokens shall **never** sync and shall **never** cross the relay. Cluster-wide access requires no token movement: MCP tools execute on the owning host, and cross-host callers reach them through the tool-call relay (R-UD12), so a single grant on the owning host serves the entire cluster.

## 10. Client Registration Ladder

Client identity for a given authorization server is resolved on the host performing registration — the resolver during a resolution attempt — in this order:

**R-MO25.** The registration ladder shall be:

1. **Config-declared `client_id`** (R-MO3) — covers both IdP-console pre-registration and a CIMD https-URL client_id. Used directly, no registration call.
2. **Dynamic Client Registration** (RFC 7591) against the authorization server's `registration_endpoint`. The registration result shall be cached per (host, authorization server) under `config/mcp-auth/`.
3. **Terminal actionable error** — when neither a `client_id` is declared nor DCR is offered, resolution fails with an error instructing the operator to register a client manually with the IdP and declare its `client_id` in `mcp.json`.

**R-MO26.** For a pre-registered client, the operator shall register the loopback web-router callback path as a `redirect_uri` with the IdP. RFC 8252 loopback redirect semantics make a loopback `redirect_uri` portable across resolving hosts (the authorization server matches the loopback host and path, tolerating an ephemeral port). An authorization server that rejects a loopback `redirect_uri` surfaces as an IdP-side error at authorize time; bound does not pre-validate the IdP's redirect policy.

## 11. Surfaces

**R-MO27.** The consent affordance shall render on the active surface of the suspended call, and a pending challenge shall be resolvable from any surface:

- **(a) boundless / TUI.** The suspension renders as a consent notice carrying the authorize URL, shaped like a client-tool confirmation.
- **(b) MCP Apps.** Tokens attach at the server-side proxy — the header-injection seam in `packages/web/src/server/routes/mcp-apps.ts` (the loop that injects configured `server.headers` into `forwardHeaders` before the upstream fetch). The iframe never holds a credential. A pending challenge renders as a consent card in the app panel; the redirect round-trips through the same web callback (R-MO17.6); a step-up mid-app is the same challenge row surfaced inline.
- **(c) Discord / web chat.** A challenge surfaces as a message carrying the authorize URL through existing delivery.
- **(d) CLI.** `bound login --challenge <id>` claims a previously-raised challenge from any machine and runs the resolver flow with a loopback callback. `bound login --mcp <server>` is sugar that raises-and-resolves synchronously for proactive warm-up of a server before first use.

**R-MO28.** The CLI and provider shall reuse the existing consent machinery — `generatePkce`, `generateState`, and the loopback `awaitCallback` from `packages/cli/src/commands/login.ts` and `packages/llm/src/drivers/chatgpt-oauth/auth-core.ts` — generalized off the hardcoded `auth.openai.com` authorize/token/redirect constants so the same primitives serve an arbitrary discovered authorization server.

## 12. Security Invariants

**R-MO29.** **No token passthrough (strong form).** No upstream access or refresh token shall ever cross the relay or a synced row. Only a single-use authorization code and its PKCE verifier make one hop, resolver → owner, and are consumed exactly once.

**R-MO30.** **Secret containment.** `client_secret` shall never leave the owner's config — not in a challenge row, not in a `durable_work` handoff, not in a synced table. Challenge rows carry no secret material of any kind (R-MO7).

**R-MO31.** **CSRF binding.** The `state` parameter shall bind the callback to its originating challenge; a callback whose `state` does not correlate to a pending challenge shall be rejected.

**R-MO32.** **Fresh PKCE per attempt.** Each resolution attempt shall mint a fresh PKCE verifier/challenge and `state`. No PKCE material is reused across attempts, and none is synced.

**R-MO33.** **Resource indicator.** The RFC 8707 `resource` parameter shall be present on both the authorize request and the token request, SDK-enforced, naming the MCP server as the intended resource so the authorization server audience-restricts the token.

**R-MO34.** **HTTPS-only endpoints.** Token endpoints shall be `https` (SEP-2207), with the loopback `redirect_uri` the sole `http` exemption (RFC 8252).

## 13. Step-Up Sequence

The full `403 insufficient_scope` step-up path, with the three deviations from the 2025-03-26 reference flow (§2) annotated at the point each occurs. Requester host, owning host, and resolving host are drawn as three distinct hosts to show the general case; any two may coincide.

```mermaid
sequenceDiagram
    participant Loop as Agent loop (requester)
    participant Owner as Owning host
    participant MCP as MCP server (upstream)
    participant Row as Challenge row (synced)
    participant Resolver as Resolving host + browser
    participant AS as Upstream AS

    Loop->>Owner: tool call (relay to owner, R-UD12)
    Owner->>MCP: MCP call
    MCP-->>Owner: 403 insufficient_scope
    Owner->>Row: raise challenge (demand)
    Owner-->>Loop: auth_challenge_raised
    Note over Loop,Owner: DEVIATION 3a — relay settles now; no token minted downstream
    Note over Loop: loop SUSPENDS on mcp:auth:{challengeId}
    Row-->>Resolver: syncs
    Resolver->>Row: claim
    Note over Resolver: DEVIATION 2 — callback will land on the RESOLVER
    Resolver->>AS: RFC 9728 PRM discovery
    Resolver->>AS: RFC 8414 AS metadata (+ DCR if needed, §10)
    Resolver->>AS: authorize (PKCE, resource)
    AS-->>Resolver: consent (browser)
    AS-->>Resolver: code via GET /oauth/mcp/callback
    Note over Resolver: correlate by state
    Resolver->>Owner: durable_work handoff: code + verifier + redirect_uri + issuer + registration
    Note over Owner,Resolver: DEVIATION 1 + 3b — only code + verifier cross; NEVER a token
    Owner->>AS: code exchange (own client credentials)
    AS-->>Owner: access + refresh token
    Note over Owner: write config/mcp-auth/{server}.json (never syncs)
    Owner->>Row: flip challenge to resolved
    Row-->>Loop: syncs; event wake mcp:auth:{challengeId}
    Loop->>Owner: re-dispatch identical call (relay to owner)
    Owner->>MCP: MCP call (Authorization: owner token)
    MCP-->>Owner: 200
    Owner-->>Loop: tool result
```

**Deviation 1** (only code+verifier cross the relay, never a token) occurs at the `durable_work` handoff: the resolver ships the code and verifier to the owner, and the owner alone holds the token that the exchange produces.

**Deviation 2** (callback lands on the resolver, not the owner) is fixed the moment the resolver claims the challenge: the authorize `redirect_uri` names the resolver's loopback web router, so the browser returns the code to the resolving host.

**Deviation 3** (no downstream token minted) has two faces: **3a**, the relay settles with `auth_challenge_raised` instead of the owning host issuing the requester any downstream credential; and **3b**, the cross-host artifact is a single-use code plus verifier, not a bearer token. The requester's later access is the tool call relaying to the owner (R-UD12), authenticated by transport keys — no minted session token exists at any point.
